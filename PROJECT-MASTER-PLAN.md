# Strength Lab — Permanent Product Vision and UX Guardrails

Status: user-confirmed direction, 2026-11-16. This document records product intent; it does not claim that the implementation is finished.

## Mission
Build a sustainable, lifelong training companion using the 719 usable Mark Wildman research transcripts as evidence. Preserve distinct movement techniques, programming methods, useful variations, and training-for-life philosophy without multiplying redundant features. The system should help users train intelligently for decades.

**Product principle: Complexity in the engine; simplicity in the experience.** The engine handles evidence, prerequisites, scheduling, progression, recovery, and realistic time budgets. The interface exposes the next useful action and a clear explanation on demand, not all of the machinery.

## Research integrity
- Account for each of the 719 usable sources and the single excluded record.
- Extract and deduplicate movement instruction, numerical methods, philosophy, and decision rules. Keep source anchors and contradictions.
- Distinguish source-supported prescriptions from app-authored adaptations.
- A linked lesson, passing regression, and verified transcript teaching are different levels of completion.
- Keep eight planned Books separate from the operational Movement Library. Book completion must not block useful Learn content.

## Product areas — user's priorities
- **Home / Train:** user likes current look and flow. Preserve; improve only where needed.
- **Workout:** user likes current experience. Preserve; prioritize reliable execution and effortless logging.
- **Training Log:** acceptable but not great. Improve the hierarchy of meaningful progress, consistency, readiness, and drill-down history.
- **Learn:** needs substantive, useful movement and programming knowledge now, independent of the unfinished eight-book publishing effort.
- **Settings:** user considers current screen cumbersome, overcomplicated, and badly organized. Major redesign required, not merely cosmetic cleanup. Necessary onboarding questions must remain available, but ordinary settings should not resemble a programming control panel.

## Settings redesign hypothesis (requires UX review before implementation)
1. **Guided first-run setup:** goals, weekly availability/time, equipment inventory, experience/readiness, and safe movement familiarity. Ask only questions that materially change the prescription; progressive disclosure and edit later.
2. **Everyday preferences:** training days/time budget, equipment changes, reminders/timers and presentation.
3. **Program & progress:** explain current training emphasis, core/developing pathways, next progression; optional advanced controls behind an explicit Advanced entry.
4. **Data & app:** export/restore, clear-data confirmation with backup opportunity, app version, troubleshooting.
Avoid duplicated controls, hidden conflicting settings, and giant forms. A user should be able to start training without mastering the algorithm.

## Development priorities
1. Permanent project-state, queue, decisions, handoff and research-integration tracking in GitHub.
2. Full transcript concept inventory, deduplication, source-to-engine gap matrix.
3. Sustainable curriculum coordinator: manageable core work plus a developing skill pathway; preserve existing progression contracts.
4. Missing source-supported methods and lifelong training decision rules.
5. Multi-year simulations and provenance verification.
6. UX redesign in staged reviews; Settings and Learn receive special attention. Preserve liked Train/Workout patterns.
7. Physical Android/offline/audio/backup acceptance before production promotion.

## Continuity contract for ChatGPT and Codex
At each development batch: read current branch/commit and project state; choose bounded work; inspect actual source; implement; run relevant regression and evidence checks; commit on preview; update queue/state and blockers. Never claim unrun tests, source completeness, or physical acceptance. Do not overwrite real training data or promote production without user approval.

## Definition of done
Every usable source is accounted for; each distinct useful concept has a destination or reasoned exclusion; all implemented methods have honest provenance and end-to-end tests; realistic longitudinal training remains sustainable; Learn is genuinely informative; Settings is simple to use; data and physical Android behavior are verified; user reviews the final interface.
